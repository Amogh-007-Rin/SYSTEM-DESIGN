# Module 09 — Common Interview Questions

**Q1: When would you choose block storage over object storage?**
Block storage is the right choice when you need low-latency random reads/writes at the byte/block level under direct OS control — primarily for database storage volumes, boot disks, and anything where the application needs to manage its own filesystem semantics. Object storage is the wrong fit there because it has no concept of in-place partial writes — every update replaces the whole object. If the workload is "many small random writes to the same file," reach for block storage; if it's "write a blob once, read it many times, never partially modify it," reach for object storage.

**Q2: Why is object storage eventually consistent (or historically was), and why does that matter?**
Object storage achieves massive horizontal scale by replicating each object across multiple machines/facilities, and historically a write was acknowledged once it landed on one replica, with the rest catching up asynchronously — meaning a read routed to a different replica immediately after a write could miss it. It matters because application code that assumes "I wrote it, so I can immediately read it back from anywhere" can have subtle, hard-to-reproduce bugs against eventually-consistent storage. (S3 itself has offered strong read-after-write consistency since December 2020, but the eventual-consistency mental model still applies broadly to distributed object stores.)

**Q3: What's the core difference between an LSM tree and a B-tree as a storage engine, and when would you pick each?**
A B-tree updates data in place, keeping one current, sorted structure on disk — fast reads (one place to look), but writes require a random-access disk operation per update. An LSM tree never updates in place: writes go to an in-memory memtable and flush sequentially to immutable SSTables, with background compaction cleaning up over time — fast writes, but reads may need to check multiple files. Pick a B-tree (PostgreSQL, MySQL) for read-heavy, query-flexible workloads; pick an LSM tree (Cassandra, RocksDB) for write-heavy workloads like logging, time-series, or event ingestion.

**Q4: What is compaction in an LSM tree, and why is it necessary?**
Compaction is a background process that merges multiple SSTables into fewer, larger ones, discarding overwritten or deleted (tombstoned) entries along the way. It's necessary because without it, the number of SSTables a read has to check grows without bound as more memtables flush, eventually making reads arbitrarily slow — compaction keeps that file count (and therefore read latency) bounded, at the cost of ongoing background disk I/O and CPU.

**Q5: AWS advertises "11 nines" of durability for S3 — what does that actually mean, and how is it different from availability?**
Durability (11 nines, 99.999999999%) is the probability that a stored object is *not lost* over a year — achieved through replicating each object across multiple devices and facilities so that losing data requires multiple independent failures at once. Availability (S3 Standard advertises around 99.99%) is about whether the *service can be reached* to serve a request right now. A system can be highly durable (your data is safe) while occasionally unavailable (a request times out) — they're separate guarantees with separate numbers, and conflating them is a common mistake.

**Q6: How does a CDN relate to an object store like S3 — are they redundant?**
No — they solve different problems. The object store is the durable origin holding every object ever uploaded, optimized for capacity and durability rather than serving millions of low-latency reads per second worldwide. A CDN caches the popular subset of that content at edge locations physically close to users, so most reads never reach the origin at all. In a typical media-heavy application, the object store is the source of truth and the CDN is the fast read path in front of it.

**Q7: What's the difference between RAID and replication, and does RAID replace the need for backups?**
RAID combines multiple physical disks on one machine into a logical volume for performance and/or redundancy at the disk level (e.g., RAID 1 mirrors a disk, RAID 5 adds distributed parity). Replication, in the distributed-systems sense, copies data across multiple machines or even multiple datacenters. RAID does not replace backups or cross-region replication — it only protects against a single disk failing, not against data corruption, accidental deletion, application bugs, or a whole machine/facility going down.

**Q8: When should you compress stored data, and what's the trade-off in choosing an algorithm?**
Compress when storage or network bandwidth cost matters more than the CPU cost of compressing/decompressing, or when I/O time saved (fewer bytes to move) outweighs the CPU time spent. The algorithm choice trades compression ratio against speed: LZ4 and Snappy are extremely fast but compress less, fitting hot paths like LSM tree SSTable writes; gzip and Zstandard compress more but cost more CPU, fitting archival or bandwidth-constrained scenarios. Zstandard is increasingly popular because its compression level is tunable, letting you pick a point on that trade-off curve explicitly.

**Q9: What's the purpose of storage tiering (hot/warm/cold), and how is it usually automated?**
Tiering matches storage cost to actual access frequency — frequently accessed data sits in fast, expensive storage (hot), occasionally accessed data sits in cheaper storage with a small retrieval cost (warm), and rarely accessed data sits in the cheapest storage with real retrieval latency (cold/archive, e.g., S3 Glacier). It's usually automated with lifecycle policies that move objects between tiers based on age or last-access time, since most data's value/access frequency naturally declines over its lifetime without anyone manually managing it.

**Q10: How would you design the metadata layer for a distributed file system, separate from the actual file data?**
The metadata layer needs to track, for every file/directory: its name and location in the hierarchy, its owner/permissions, and which physical chunks/nodes hold its actual data — fundamentally a small-record, high-query-rate database problem, distinct from the bulk-data storage problem. GFS and HDFS centralize this in a single master/NameNode for simplicity, accepting it as a potential bottleneck and single point of failure (mitigated via standby replicas and periodic checkpointing) in exchange for a much simpler consistency model than fully distributing metadata would require. This trade-off — and how to remove the single-master limitation — is explored directly in [Design Challenge 02](../04-exercises/design-challenges/challenge-02.md).
