# Module 19 — Common Interview Questions

**Q1: What's the difference between how ML systems fail and how traditional systems fail, and why does it matter for design?**
A traditional system generally fails loudly — a bug throws an exception, a service returns a 500, a crash shows up immediately in error-rate monitoring. An ML system can be running 100% correct code and still degrade silently, because its behavior depends on a learned relationship between input data and outputs, and that relationship can stop matching reality as the world changes (data drift, concept drift) with zero code changes and zero errors thrown anywhere. This is why ML systems need a category of monitoring (drift detection, prediction distribution tracking) that has no real analog in traditional infrastructure monitoring — normal monitoring is structurally blind to "the model is just wrong now."

**Q2: What is a feature store, and what specific problem does it solve?**
A feature store is a centralized system for defining, computing, and serving the inputs ("features") a model consumes, materialized into two stores: an offline store (batch-optimized, used for training) and an online store (low-latency, used for real-time inference). It exists to solve **training-serving skew** — the failure mode where the feature computation logic used during training and the feature computation logic used during serving are implemented twice (often by different people, at different times) and quietly diverge, so the model sees systematically different inputs in production than it learned from, degrading accuracy with no error in any log.

**Q3: Why do you need both an online and an offline feature store — isn't that redundant?**
They're not storing conceptually different data — they're materializing the *same* feature definitions for two incompatible access patterns. The offline store needs to serve large, point-in-time-correct batch reads efficiently (e.g., "this feature for 10 million users as of various historical timestamps," for training); the online store needs single-key point lookups in single-digit milliseconds (for live inference). No single storage technology is good at both. The redundancy is deliberate and is exactly the mechanism that prevents skew, provided both stores are populated from one shared feature definition rather than two independent implementations.

**Q4: When would you choose batch inference over real-time inference, and vice versa?**
Choose batch inference when predictions don't need to reflect the very latest input data and can be computed on a schedule — e.g., nightly churn-risk scores, a weekly recommendation refresh — because it's cheaper and lets you fully utilize batch compute hardware without a per-request latency SLA. Choose real-time inference when the input is only known at request time and the use case has a genuine low-latency requirement — fraud-scoring a transaction as it happens, ranking live search results. Defaulting to real-time "to be safe" without a real latency requirement is a common over-engineering mistake; real-time serving is meaningfully more operationally expensive (always-on capacity, strict SLAs, online feature store dependency).

**Q5: What's the difference between collaborative filtering and content-based filtering, and what's each one's main weakness?**
Collaborative filtering recommends based on behavioral similarity ("users who liked X also liked Y"), typically via matrix factorization of a sparse user-item interaction matrix; its weakness is the cold-start problem — a new user or item has no interaction history to factorize. Content-based filtering recommends based on item attributes (genre, metadata, text) matched to a user's profile; it solves cold-start for new items (which have metadata immediately) but tends to over-recommend more of the same and misses the cross-category affinities collaborative filtering can pick up purely from behavior. Most production systems blend both.

**Q6: How does a two-tower model make recommendation serving scalable, and why can't you just score every item for every user directly?**
Scoring every item for every user with a single combined model is computationally infeasible at real-time latency once the catalog reaches millions of items. A two-tower model uses two independent neural networks — a user tower and an item tower — that each produce an embedding in the same vector space, trained so a user's embedding is close to items they engaged with. Because the towers are independent, all item embeddings can be precomputed and indexed offline; at serving time you only compute one user embedding and run an approximate nearest neighbor search against the precomputed item index — turning an O(catalog size) per-request problem into one embedding computation plus a sub-linear vector search.

**Q7: What's the difference between FAISS and HNSW, and why does approximate nearest neighbor search exist at all?**
Exact nearest neighbor search means comparing a query vector against every indexed vector — cost scales linearly with corpus size, which becomes a real bottleneck (too slow for a real-time budget) once a corpus reaches millions of vectors. FAISS is a library implementing several approximate strategies, notably IVF (clustering vectors into partitions and searching only the nearest partitions at query time), often combined with product quantization to compress memory footprint. HNSW builds a multi-layer graph connecting each vector to its approximate neighbors, searching from a sparse top layer down into denser layers to converge on near-exact neighbors in roughly logarithmic time. Both trade a small, tunable amount of recall (occasionally missing the true single closest vector) for orders-of-magnitude speed gains — an acceptable trade-off because returning the 2nd-closest item out of a top-k list is harmless for recommendation or retrieval.

**Q8: What are data drift, concept drift, and prediction drift, and how do they differ?**
Data drift is a change in the distribution of input features (e.g., spending patterns shift after a major world event). Concept drift is a change in the relationship between inputs and the correct label, even when the inputs look statistically unchanged (the same transaction pattern that was benign last year now indicates a new fraud technique). Prediction drift is a change in the distribution of the model's own output predictions, which can be a visible symptom of either of the other two. Data and prediction drift can be detected immediately from live distributions with no ground-truth labels required; concept drift is the hardest to catch because it requires new labels (often arriving with real-world delay) to notice the input-output relationship itself has shifted.

**Q9: What is a KV cache in LLM inference, and why does it matter for serving cost and capacity planning?**
Autoregressive LLMs generate one token at a time, and naively, computing attention for each new token would require recomputing attention over the entire sequence generated so far — quadratically wasteful as sequences grow. The KV cache stores the key/value attention vectors for every previously processed token so each new token only needs one incremental computation. The trade-off is that the KV cache itself consumes substantial GPU memory, growing with both sequence length and concurrent batch size — its memory footprint is one of the primary numbers that caps how many simultaneous requests a given GPU can serve, making it a central capacity-planning concern in LLM infrastructure, not just an implementation detail.

**Q10: What are the four stages of a RAG pipeline, and which run offline versus online?**
Chunking (splitting source documents into smaller passages) and the embedding pipeline (encoding each chunk into a vector) run **offline**, once per document at ingestion time, with results stored in a vector database (Pinecone, Weaviate, pgvector). Retrieval (embedding the user's query and finding the top-k most similar chunks) and generation (inserting those chunks into the LLM's prompt and generating an answer) run **online**, per user query. Keeping these two pipelines conceptually and operationally separate — one is a batch/streaming data pipeline, the other is a latency-sensitive request path — is foundational to designing RAG correctly; conflating them (e.g., re-embedding documents per query) would make the system both slow and needlessly expensive.
