# Module 17 — Common Interview Questions

**Q1: What's the core difference between batch and stream processing, and how do you decide which one a system needs?**
Batch processing operates on a complete, bounded dataset that already exists at rest, producing one result when the job finishes — minutes to hours later. Stream processing operates on an unbounded sequence of events, producing incremental results within milliseconds to seconds of each event arriving. The deciding factor is the latency requirement implied by the use case: a monthly billing reconciliation only needs batch's eventual completeness; a fraud check on a live transaction needs stream's low latency, even if that means accepting results that might later need correction.

**Q2: Explain the Lambda architecture and name its biggest practical drawback.**
Lambda architecture runs the same data through a batch layer (scheduled, accurate, delayed) and a speed layer (continuous, approximate, low-latency) simultaneously, with a serving layer merging both for queries — recent data comes from the fast-but-approximate speed layer, older data comes from the slow-but-accurate batch layer once it catches up. Its biggest drawback is maintaining two separate codebases implementing essentially the same transformation logic (once in a batch framework like Spark, once in a stream framework like Flink), which inevitably drift apart over time as one is updated and the other is forgotten.

**Q3: What is the Kappa architecture, and why was it proposed?**
Kappa architecture, proposed by Jay Kreps as a direct response to Lambda's dual-codebase problem, treats everything as a stream — including historical reprocessing. Instead of a separate batch layer, if results need to be recomputed from scratch, the historical event log (typically Kafka, retaining enough history) is replayed from the beginning through the *same* streaming job that handles live data. This collapses Lambda's two codebases into one, at the cost of needing a stream processor capable of handling a full historical replay and a log retention policy that covers however far back reprocessing might need to reach.

**Q4: What's the difference between ETL and ELT, and when would you choose each?**
ETL (Extract, Transform, Load) transforms data in a dedicated processing layer before loading it into the destination, which fits sources needing heavy upstream cleaning or destinations with limited compute. ELT (Extract, Load, Transform) loads raw data first and transforms it inside the destination using the warehouse's own query engine — this fits modern cloud warehouses (Snowflake, BigQuery) with cheap, elastic compute, and has the advantage of preserving raw data so transformation logic can be revised later without re-extracting from the source.

**Q5: What is Change Data Capture, and why is it preferred over having the application publish events directly?**
CDC reads a database's existing transaction log (the WAL/binlog every database already maintains for crash recovery) and converts committed changes into a stream of events, without any change to the application that writes to the database. The alternative — having application code explicitly publish an event on every write — suffers from the dual-write problem: a crash between the database write and the event publish leaves the two inconsistent, and every code path touching the database must remember to also publish. CDC sidesteps this because the transaction log is always accurate and already exists; nothing can be written to the database without eventually appearing in the log.

**Q6: Explain a star schema — what's a fact table versus a dimension table, and why is this schema deliberately denormalized?**
A fact table holds one row per business event (a sale, a trip, a click) and is mostly numeric measurements plus foreign keys into dimension tables. Dimension tables hold descriptive context about the entities involved (customers, products, dates) and change far less often than the fact table grows. The schema is deliberately denormalized — e.g., a product's category name is duplicated across every row referencing that product rather than normalized further — because that trade-off makes the join patterns analytical queries need (aggregate by category, by month, by region) simple and fast for a query engine to plan, at the cost of redundant storage that a normalized OLTP schema would avoid.

**Q7: Why are column-oriented formats like Parquet and ORC faster for analytics than row-oriented storage?**
Row-oriented storage keeps every column of a row contiguous, so fetching one full row is fast, but an analytical query needing only a few columns out of many still has to read every row's full set of columns. Column-oriented formats store each column's values contiguously across all rows, so a query needing 3 of 50 columns reads only those 3 columns' data, and similar values within a single column compress far more efficiently than heterogeneous row data. Combined with predicate pushdown — using per-block min/max statistics to skip blocks that can't match a filter — this is why analytical engines reading Parquet/ORC can be an order of magnitude faster than scanning row-oriented data for the same query.

**Q8: What's the difference between a data lake, a data warehouse, and a data lakehouse?**
A data warehouse stores structured data with schema enforced before loading, optimized for fast, governed SQL analytics, but historically expensive at huge scale and rigid about what it can hold. A data lake stores any format cheaply in object storage with schema interpreted at read time, which is flexible but prone to becoming an ungoverned "data swamp" without discipline. A data lakehouse stores data in open columnar formats on cheap object storage like a lake, but adds a transactional metadata layer (Delta Lake, Iceberg, Hudi) providing ACID transactions, schema enforcement, and time travel — aiming to get warehouse-grade reliability without copying data into a separate proprietary system.

**Q9: What problem does Apache Airflow solve, and what does "DAG-based" actually mean in practice?**
Airflow orchestrates multi-step pipelines where steps have dependencies on each other (extract from several sources, wait for all of them, transform, load, then report) — it schedules tasks, runs independent tasks concurrently, retries failures, and provides visibility into a pipeline's current state. "DAG-based" means the pipeline is modeled as a directed acyclic graph of tasks: edges express "this task must finish before that one starts," and the graph must have no cycles, since a cycle would mean no task could ever be first. Airflow itself doesn't process data — it triggers and sequences external systems (Spark jobs, SQL queries, API calls) and handles the order, retries, and alerting around them.

**Q10: A pipeline needs to process 100K events/second with sub-500ms latency for fraud detection. What architectural decisions does that latency number force?**
Sub-500ms latency rules out batch processing entirely (batch jobs run on minutes-to-hours cycles) and rules out Lambda's batch layer as anything but a background accuracy-correction mechanism — the actual fraud decision has to be made entirely within a streaming/speed-layer path. It pushes toward a Kappa-style architecture (one streaming codebase, simpler to keep the decision logic consistent) or Lambda's speed layer alone for the real-time decision, with a dedicated stream processor (Flink, given the need for stateful per-account/per-card windowed aggregation) reading from a high-throughput log (Kafka, partitioned to parallelize the 100K events/second across many consumers). It also forces explicit choices about what state must be kept in memory (recent transaction history per account) versus looked up externally, since a network round-trip to an external database for every single transaction at that throughput would itself threaten the latency budget.
