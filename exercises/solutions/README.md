# A Note on Solutions

Every coding challenge's `solution.ts` is a complete, working reference implementation. Every design challenge's `challenge-NN-solution.md` is a full worked answer. They are intentionally kept alongside the problems (inside each module's `04-exercises/` folder) rather than hidden in a separate repository, because this is an open educational resource, not a graded course.

That said, the value of an exercise comes almost entirely from the attempt, not the answer key. Before you open a solution:

> ⚠️ **Warning:** Reading a solution before attempting the problem will make you feel like you understood it. Implementing it yourself — and getting it wrong at least once — is what actually builds the skill. System design interviews reward the ability to *derive* a correct approach under pressure, not the ability to recognize a memorized one.

## Suggested Discipline

1. Read the problem statement (`README.md` or `challenge-NN.md`) fully before looking at any code.
2. For coding challenges: try to fill in every `// TODO:` in `starter.ts` yourself, and run it against the `// === USAGE EXAMPLE ===` block until your output matches the expected behavior described in the comments.
3. For design challenges: write down your own requirements, estimation, and architecture — even just bullet points — before reading the solution.
4. Only then, open `solution.ts` or `challenge-NN-solution.md` and compare. Look specifically for places where your approach differs and ask *why* — sometimes you found a valid alternative, sometimes the solution caught an edge case you missed.

## Contributing New Solutions

If you find a bug in a solution, or want to propose an alternative valid implementation, see [CONTRIBUTING.md](../../CONTRIBUTING.md). Alternative solutions are welcome as long as they're clearly marked as alternatives and don't replace the primary reference implementation.
