# Module 13 — Common Interview Questions

**Q1: State the CAP theorem precisely. Why is "pick two of three" a misleading way to describe it?**
A distributed data store can provide at most two of Consistency, Availability, and Partition tolerance *simultaneously during a network partition*. "Pick two of three" is misleading because partition tolerance isn't optional — in any real distributed system spanning more than one node, the network will eventually drop or delay messages. You don't choose whether partitions happen; you only choose what your system does *when* one happens. So the real, only choice is CP vs. AP during a partition. CA is not a real option for a multi-node system — it only exists for systems with nothing to partition (single-node).

**Q2: Classify Cassandra, ZooKeeper, and a single-node PostgreSQL instance as CP, AP, or CA. Justify each.**
ZooKeeper is CP — a minority-side partition can't process writes at all; it sacrifices availability to guarantee every answer is correct, which matters for its use case (distributed locks, where a stale answer is far worse than no answer). Cassandra is AP by default — any reachable replica answers immediately, even if it might be stale, because it's tuned for high availability across distributed deployments; it does offer tunable consistency levels, but its default posture favors availability. A single-node PostgreSQL instance is CA — and this is the *correct* answer specifically because there's nothing to partition; the instant you add a replica for failover, you reintroduce partition risk and must pick CP or AP for that replication.

**Q3: What does PACELC add that CAP doesn't cover?**
CAP only describes behavior *during* a partition. PACELC observes that even with *no* partition, a distributed system still trades latency against consistency on every single write: wait for all replicas to acknowledge (favoring consistency, paying a latency cost on every write) or confirm immediately and replicate asynchronously (favoring latency, at the risk of a reader seeing stale data even with zero partition in sight). Cassandra is PA/EL (available during a partition, low-latency in normal operation); a system with synchronous multi-region replication is PC/EC (consistent in both regimes, paying a constant latency tax for it).

**Q4: Walk through how Raft elects a leader, including why the election timeout is randomized.**
Every node starts as a follower running a randomized election timeout (e.g., 150–300ms). If a follower hears nothing from a leader before its timeout fires, it becomes a candidate, increments its term, votes for itself, and sends `RequestVote` RPCs to every other node. Nodes grant one vote per term to the first candidate they hear from. If the candidate gets votes from a majority, it becomes leader and starts sending heartbeats. The timeout is *randomized* specifically so that it's statistically unlikely two followers time out at the exact same moment and split the vote — while still guaranteeing some node eventually times out first and wins cleanly. If a split vote does happen anyway, it's not a failure: terms increment, timeouts reshuffle randomly, and another round runs until one candidate wins a clean majority.

**Q5: What's the difference between linearizability and eventual consistency, and why is linearizability expensive to provide?**
Linearizability guarantees that once any client's write completes, every subsequent read from any client anywhere sees that write or a later one — operations appear to happen instantaneously at one point in real time, with no window where two clients see different "current" answers. Eventual consistency only guarantees that *if writes stop*, all replicas will *eventually* converge, with no bound on how long and no guarantee about what a read sees in the meantime. Linearizability is expensive because enforcing it requires ordering every operation relative to every other operation system-wide, typically by routing operations through a single coordination point (a leader or a consensus round on every operation) — which is both a latency cost (every operation may need a round trip to that point) and, per CAP, an availability risk during a partition.

**Q6: How does a CRDT guarantee convergence without coordination? Name the three properties its merge function must satisfy.**
A CRDT's merge operation must be commutative (order of merging doesn't matter), associative (grouping of merges doesn't matter), and idempotent (merging the same update twice doesn't change the result). Because of these three properties, every replica can accept writes locally with zero coordination, exchange state with other replicas in any order, any number of times, and all replicas are mathematically guaranteed to converge to the identical result — no consensus protocol, no leader, no conflict left over for an application to resolve.

**Q7: Would you choose a CP or AP database for a distributed shopping cart? Defend your answer against a concrete failure scenario.**
AP, modeled with a CRDT (an OR-Set of line items) rather than a single overwritable field. Scenario: a user's phone and laptop both have the cart open during a network partition; the phone adds a USB cable, the laptop adds a laptop stand, concurrently. A CP cart would have to block one of those writes (whichever device couldn't reach quorum) — refusing to let the user shop is a worse experience than the actual risk here. An AP cart with an OR-Set merge lets both writes succeed locally and immediately, and when the partition heals, set union naturally preserves both additions with no conflict to resolve and no data silently dropped. **Q8: What's the difference between what a vector clock tells you and what a CRDT does for you?**
A vector clock *detects* whether two versions of data are causally related (one is a strict descendant of the other, safe to resolve automatically by keeping the newer one) or truly concurrent (neither saw the other's write — a genuine conflict). It does not resolve that conflict for you — once it flags two versions as concurrent, the application still has to decide what to do (show both to the user, merge manually, pick a policy). A CRDT is designed so that there is never an unresolved conflict in the first place — its merge function is defined for *any* pair of states and produces a deterministic, agreed-upon result automatically, with no separate detection step and no app-level decision required.

**Q9: When is consensus (Raft/Paxos) actually necessary, versus when would a CRDT be the better tool?**
Consensus is necessary when there must be exactly one agreed-upon answer or ordering — leader election (only one node can be "the leader" at a time), a replicated log where every node must apply operations in the identical order, or a unique resource allocation (only one process can hold a specific lock). A CRDT is the better tool when the data can be modeled so that *all* concurrent updates are individually valid and only need to be combined, not ordered or arbitrated — counters, sets, collaborative text edits. Reaching for consensus when a CRDT would do costs you availability and latency for no benefit; reaching for a CRDT when you actually need a single source of truth (e.g., "who is allowed to debit this account right now") will produce incorrect behavior.

**Q10: A split vote happens during Raft leader election — is that a bug?**
No — it's an expected, self-healing part of the protocol, not a safety violation. It happens when multiple candidates' randomized timeouts fire close enough together that votes split across them and no one gets a majority in that term. The term number increments, each node's randomized timeout reshuffles, and another election round runs. Raft tolerates this by design specifically because the timeout is randomized — split votes become statistically rarer with each retry, and the protocol makes no progress-safety promise that's violated by taking a few rounds to elect a leader, only that *whoever* is eventually elected has a legitimate majority.
