# Module 16 — Common Interview Questions

**Q1: What's the difference between WebSockets, Server-Sent Events, and long polling, and how do you choose between them?**
WebSockets are a single persistent connection supporting full bidirectional push — use them when the client needs to send data back over the same low-latency channel (chat, multiplayer, collaborative editing). SSE is a one-directional server-to-client stream riding on plain HTTP, with built-in reconnection — use it for feeds, notifications, and dashboards where the client never needs to push data back over the same channel. Long polling is a held-open HTTP request used as a compatibility fallback when neither of the above is reliably supported by the client's network path — it works almost anywhere but costs more overhead per "no new data" cycle.

**Q2: A single WebSocket server works fine in a demo. What breaks when you put a second instance behind a load balancer, and how do you fix it?**
Two things break: routing (a plain round-robin load balancer can send a client's reconnect to a *different* instance than the one holding its original socket — fixed with sticky sessions) and delivery (an event relevant to a connection on instance B has no way to reach instance B from instance A's process, since they don't share memory — fixed with a shared pub/sub backbone like Redis Pub/Sub, where every instance publishes events to a shared channel and each instance independently delivers to whichever of its own local connections care).

**Q3: What is the "fan-out problem," and how do large systems deliver one event to millions of subscribers without one process trying to write to millions of sockets directly?**
Fan-out is delivering a single event to a very large number of subscribers efficiently. Rather than one process writing to every socket, the event is published once to a shared pub/sub backbone, which fans out to N server instances, each of which then fans out only to the (much smaller) set of sockets it personally holds — bounding the real per-process load to "connections per instance," not the global subscriber count.

**Q4: How does a presence system detect that a user has gone offline, given that a dropped connection (lost signal, killed app) doesn't always send a graceful disconnect message?**
Via a heartbeat mechanism: the client periodically sends a small "still here" signal, and the server tracks a per-user last-seen timestamp, commonly implemented as a TTL key in a fast store like Redis that the heartbeat refreshes. If the TTL expires without a refresh, the user is considered offline. This means presence accuracy is bounded by the heartbeat interval and timeout — there's always a small window where the system believes someone is online slightly after they actually disconnected.

**Q5: Why can't you reliably order chat messages using each client's local timestamp?**
Clock drift between devices means client-reported send times aren't guaranteed to be consistent with the order messages were actually sent or should be displayed in — a reply could show a timestamp earlier than the message it's replying to. The fix is a per-conversation monotonically increasing sequence number assigned by a single source of truth (the database or a sequence service), with client timestamps used only for display, never for ordering.

**Q6: How would you implement read receipts efficiently for a group chat with many members?**
Track only a high-water mark per (user, conversation) pair — "user X has read through message sequence N" — rather than a boolean flag per individual message per user. Since sequence numbers are monotonic, "read through #482" implies every earlier message is also read, avoiding the need to store and update one flag per message per group member.

**Q7: When would you choose SSE over WebSockets even though WebSockets can do everything SSE can and more?**
When the requirement is genuinely one-directional (a live score feed, a notification stream, a dashboard) — SSE rides on plain HTTP with no protocol upgrade, gets automatic client reconnection for free via the browser's `EventSource` API, and works transparently through existing HTTP infrastructure (proxies, load balancers, CDNs) without anything needing to be WebSocket-aware. Reaching for WebSockets when you'll never use the upstream channel adds operational complexity (connection-state management, sticky sessions, pub/sub backbone) for a capability you don't need.

**Q8: Why is push notification delivery (APNs/FCM) architecturally different from in-app real-time delivery?**
In-app delivery uses a connection the app already holds open while in the foreground — your own infrastructure (WebSocket/SSE) delivers directly. Push notifications must reach a device even when the app isn't running at all, which your backend cannot do directly; instead, you hand the message to the OS vendor's own persistent-connection service (APNs for iOS, FCM for Android), which is the only entity actually maintaining a connection to a backgrounded or closed app, and it handles delivery and waking the app.

**Q9: What's the difference between fan-out-on-write and fan-out-on-read in a real-time delivery context, and what's the trade-off?**
Fan-out-on-write pushes an event to every subscriber's connection the instant it happens — lowest latency per recipient, but the work scales with subscriber count at the exact moment of the event, which can spike under a sudden surge of viewers. Fan-out-on-read instead has subscribers pull/poll for current state, which is cheaper to scale (the same cached value serves many readers) but reintroduces latency and some of the inefficiency real-time push exists to avoid.

**Q10: Why is collaborative editing (e.g., Google Docs-style) a harder real-time problem than a live stock ticker, even though both broadcast frequent updates to many viewers?**
A stock ticker only cares about the *current* value, so rapid updates can be safely coalesced — if the price changes 10 times in 100ms, broadcasting only the latest is fine. Collaborative editing cannot make that simplification because every individual edit matters and concurrent edits from different users must be merged into one consistent result, requiring conflict-resolution algorithms (Operational Transformation or CRDTs) rather than simply broadcasting the latest state and discarding the rest.
